### 0.3 写作总原则（"只写真实"）

1. **数字带口径**：本手册工程数字均为 2026-10-17 本机实测，复现命令见附录 B；论文里写"截至 20xx 年 xx 月"。
2. **只写代码里真实存在的实现**：4.4 节列了"不要写"清单，逐条对照。
3. **区分"验证过"与"没验证过"**：只在 Chrome 上跑过就不写"兼容主流浏览器"；没压测就不写响应时间。
4. **不编造对比实验**：未与其它系统做 A/B，不写"相比传统方式提升 xx%"。
5. **双盲优先于好看**：任何可能暴露身份的信息一律清除，见第 9 章。

## 1. 河北农业大学校方要求

### 1.1 已核实的流程要求（校教字〔2004〕28 号）

> 来源：《河北农业大学本科毕业论文（设计）管理规定》（校教字〔2004〕**28 号**）全文，见 [作物学实验教学中心·规章制度页转载](https://jdhtxx.com/html/menugzzd14.html)（该站页脚标注"河北农业大学"、链接回农大教务与主站，正文含文号与 12 个附件清单，可信度高；但属**二手转载**，最终以学院下发件为准）。

| 项 | 校方要求 | 我们的动作 |
|---|---|---|
| 撰写主体 | 论文（设计）由学生本人**计算机排版、打印**；**每学院有统一封面格式** | 封面必须用学院版，不自制 |
| 规范依据 | 见《河北农业大学本科毕业论文规范》《河北农业大学本科毕业设计规范》 | **这两个文件需校内取**（见 1.6） |
| 必备材料 | 开题报告（附件 1-2）、任务书（附件 4）、毕业设计封面（附件 5）、评阅书（附件 6-9）、答辩评分表（附件 10）、答辩评分标准（附件 11-12） | 答辩前按学院清单备齐 |
| 评阅 | 评阅教师须硕士/讲师及以上；由学院答辩委员会指定或聘请 | 无需我们操作 |
| **答辩形式** | 学生**用 15—20 分钟**报告论文，**用 15—20 分钟**回答委员提问；答辩小组 4—5 人 | 按 15 分钟准备（若学院近年压缩为 8~10 分钟，用 8.2 的裁剪版） |
| 成绩 | 百分制：优秀 90-100 / 良好 80-89 / 中等 70-79 / 及格 60-69；答辩委员会评定 | 目标 ≥80（良好） |
| 校级优秀 | 每届评选 **3%** 为校优秀论文，经教务处审定集辑成册 | 推优需高质量 + 低重复率 |
| 红线 | **严禁网上抄袭，一经发现严肃处理** | 见第 6 章 |
| 附件齐全 | 开题报告/评阅书等格式见附件 | 校内下载 |

### 1.2 系统与平台（已核实）

- **知网「毕业设计（论文）管理系统」**：教务处首页快捷入口（`co2.cnki.net/Login.html?dp=hebau`）→ 选题、任务书、开题、中期、**查重、送审、答辩稿**大概率都在这套系统流转，**模板也通常在系统内下载**。
- 检索中还发现第三方站点把"河北农业大学"列入**维普（VGMS）毕设管理系统**客户名单（[vgms.fanyu.com](https://vgms.fanyu.com/)）——与知网入口**冲突**，需以学院通知为准（可能一校多系统：知网做管理、维普/知网做查重）。
- 结论：**查重与送审走哪个系统、阈值多少，以知网系统内"检测报告单"与学院通知为准**，不要按网上流言准备。

### 1.3 篇幅与结构

- **字数**：用户已定 **8000 字左右**（农大公开文件未见硬性字数条款，工科 8000 字属安全区间）。
- **结构**：按学院模板；本手册第 2 章给出"可套进任何学院模板"的 8 章骨架。
- **装订顺序（待模板确认）**：通用为 封面 → 诚信声明（部分校有）→ 中文摘要 → 英文摘要 → 目录 → 正文 → 参考文献 → 附录 → 致谢。农大公开文件只明确"每学院统一封面"，**其余顺序请按学院模板核对**。

### 1.4 查重（⚠️ 阈值待确认）

| 项 | 现状 | 我们的策略 |
|---|---|---|
| 检测系统 | 知网系统内检测（校入口在知网） | 按知网报告单"总文字复制比"看 |
| 阈值 | **公网未查到农大校发阈值** | **按最严准备：≤10%**，留足余量（学院若要求 ≤20%/≤30% 我们更稳） |
| 检测范围 | 一般为 篇名 + 关键词 + 中英文摘要 + 正文 | 摘要与正文同等对待，不抱侥幸 |
| 次数 | 通常 1~2 次（系统内限制） | 先自查（学院免费检测或知网个人版）再上传，别浪费次数 |

> 参考其它院校公开区间：多数 **≤20%~30% 合格**，优秀论文线更严。我们按 ≤10% 做，天然安全。

### 1.5 双盲（已定，按最严执行）

- 送审/评阅阶段通常要求**隐去作者与导师身份**：封面、页眉页脚、致谢、附录、文档属性、PDF 元数据都要查。
- "双盲是否要求删除致谢"各院不同——**默认保留但匿名化**（只写"导师""同班同学"），**提交前向学院确认**。
- 详版清单见**第 9 章**。

## 3. 逐章写作卡

> 每卡四要素：**写什么 / 字数 / 图表位 / 素材路径**，末尾**扣分点**。
> 路径均相对仓库根 `D:\毕设\校园二手平台交易系统`。

### 3.0 摘要与 Abstract（350~450 字 / 300~400 words）

- **四段**：① 背景问题（校园闲置靠群聊贴吧：信息分散、身份不可信、无交易凭证、纠纷无处理）；② 本文工作（含校园认证、三态交易〔出售/求购/交换〕、信用互评、实时私信、举报与后台处置的校园二手交易系统；Spring Boot 3.5 + MyBatis-Plus + MySQL 8 + Redis + WebSocket，前台/管理端均 React 19 + TS）；③ 关键设计（自研 JWT + 注解鉴权、唯一约束 + 事务原子性、派生字段可重建、DFA 敏感词、离线推荐 + 缓存、WS 先落库再推送）；④ 验证与结论（**29 测试类 / 251 单测 / 124 接口 / 前台 38 条 E2E + 后台 12 项验收**）。
- **关键词**：校园二手交易；Spring Boot；React；WebSocket；信用机制
- **扣分点**：出现"首先…然后…最后…"；写未实现的 AI/区块链；中英文不一致

### 3.1 第 1 章 绪论（900~1000 字）

- **1.1 背景与意义**（300）：校园闲置高频低值、毕业季集中；现有渠道信息沉底、身份不可核、无凭证；本文把"认证—发布—撮合—面交—评价—信用"闭环进系统。
- **1.2 研究现状**（350）：三条线并**每条挂引用**——① 校园/闲置交易平台研究；② 信用与信任机制；③ Web 实时通信。别写"国外先进国内刚起步"的空话。
- **1.3 研究内容与主要工作**（200）：4~5 条，逐条对应第 6 章小节。
- **1.4 论文组织结构**（150）：逐章一句话。
- **图表位**：无（可用第 4 章架构图代）
- **素材**：`需求规格说明书-v2.md` §1/§2.1、`模块清单.md` §1
- **扣分点**：写了 800 字还没说自己做了什么；现状无引用

### 3.2 第 2 章 相关技术与开发环境（800~900 字）

- **2.1 选型思路**（180）：前后端分离、REST + 统一信封、双端 React、单库 + Redis 缓存；写**为什么**（周期/维护/答辩可讲清）。
- **2.2 后端**（200）：Spring Boot 3.5.16、MyBatis-Plus（条件构造器/分页/逻辑删除）、MySQL 8（InnoDB/事务/生成列）、Redis（推荐缓存等实际用途）。
- **2.3 前端**（200）：React 19 + TS + Vite 6 + Tailwind 4 + shadcn/ui + React Router 7 + RTK Query；说明前台由 Vue3 重构为 React 的取舍（统一技术栈、类型安全），**旧版仍在仓库可对照**。
- **2.4 关键支撑技术**（200）：JWT（jjwt，access 2h/refresh 7d）、WebSocket（会话注册表 + 按用户推送）、DFA 敏感词热更新、定时任务（推荐重算/计数重建/孤儿扫描）。
- **2.5 环境**（100）：JDK 21 / Maven / Node 20 / MySQL 8 / Chrome；端口 8080、5173、5174。
- **图表位**：表 2-1 技术栈与版本（8~10 行）
- **素材**：`backend/pom.xml`、`frontend-web-react/package.json`、`frontend-admin/package.json`
- **扣分点**：抄官网介绍；写没用到的技术（Docker/K8s/Vuex）

### 3.3 第 3 章 需求分析（1200~1300 字）

### 8.3 12 个必被问的问题（答案要点）

| # | 问题 | 要点（3 句内） |
|---|---|---|
| 1 | 为何不用 Spring Security？ | 单体+REST、需求简单；拦截器+注解即可；避免过滤器链复杂度，便于讲解排错 |
| 2 | "一帖一条待处理应约"怎么保证？ | 生成列唯一约束兜底；拒绝/撤回后生成列为空可再提交；服务层再校验 |
| 3 | 原子接受怎么做的？ | 行锁 + 单事务完成帖状态/回填订单/批量拒绝/建单；失败回滚 |
| 4 | 订单号为何不用自增/时间戳？ | 可读可追溯不暴露总量；每日序列表两步取号避免首单为 0 |
| 5 | 推荐为何离线算？ | 在线聚合开销大；定时重算 heat 并预热缓存；接口直读，冷启动兜底 |
| 6 | 软删与孤儿扫描关系？ | 内容不物理删（状态+四元组）；多态引用只做逻辑外键；每日扫描只告警不删 |
| 7 | SWAP 为何双方确认？ | 双向交付，单方完成不代表成立；各自打点都确认才完成；重复确认不重复加分 |
| 8 | 敏感词如何热更新？ | DFA 自动机；词库变更后重建；各文本入口统一校验并返回命中词 |
| 9 | 派生计数会算错吗？ | 事实表+唯一约束+事务内增减；每日重建兜底，可从事实恢复 |
| 10 | 受限/封禁如何分层？ | 封禁在拦截器层（含白名单）；受限在各业务入口（下单/发布/应约/发起交换） |
| 11 | 为何前台从 Vue 重构为 React？ | 与后台统一栈与令牌、TS 降低契约错误；旧版保留可对照，接口零变更 |
| 12 | 怎么证明系统真跑起来？ | 真 MySQL+真后端+无头 Chrome 自动化：251 单测、124 接口探针、38 条 E2E、12 项后台验收，现场可复现 |

> 三条"软"问题：① 工作量（53 需求/124 接口/27 表/1.3 万行后端+双端前端+251 测试）；② 创新点（**约束驱动的正确性设计**：生成列唯一、原子接受、可重建派生、双确认）；③ 不足（照 8.2 答，别硬撑）。
