## 11. 答辩问答备选点（基于项目真实实现）

1. **为什么不用 Spring Security，而自研 JWT？**
   项目为单体 + RESTful，鉴权需求简单：`JwtUtil` 签发 access(2h)/refresh(7d)，`AuthInterceptor` 配合 `@RequireAuth`/`@RequireRole` 注解与 `UserContext` 完成接口级鉴权，避免引入 Spring Security 的过滤器链复杂度与学习成本（见 `模块清单.md` §2 与 handoff Decisions）。管理员 RBAC 在同一拦截器内按 `@RequireRole` 校验。

2. **T8"同一帖最多一条待处理应约"和"原子接受"怎么保证？**
   数据库层用生成列唯一约束 `uk_offer_pending` / `uk_swap_req_pending` 兜底（拒绝/撤回后生成列为空可再次提交）；服务层接受时 `selectByIdForUpdate` 行锁 + 事务内原子操作：帖改 `DEALT`、被接受应约回填 `order_id`、其余待处理批量拒绝、生成订单，任一步失败整体回滚（`WantSwapAtomicityIntegrationTest` 真实 MySQL 验证）。

3. **订单号为什么用"每日序列表"而不是自增或时间戳？**
   `order_no_seq` 按业务日期取号，采用两步式 `INSERT IGNORE` + `UPDATE`（T11）：先确保当天行存在再自增。这样订单号形如 `SH20261002000003`（日期+当日序号），可读、可追踪且不暴露总量；实测取号 1→2→3，避免了单语句 upsert 当天首次返回 0 的坑。

4. **推荐为什么离线算并写 Redis？**
   PRD §6.6 要求推荐接口从 Redis 直接读、响应 <100ms。`RecommendTask` 每小时离线重算 `heat_score` 并预热热榜/活跃用户个性化缓存，`RecommendController` 只读缓存；冷启动/新用户走热门兜底。避免了每次请求实时聚合行为表的开销。

5. **软删和孤儿扫描是什么关系？**
   内容类数据不物理删除（`goods/want_post/swap_post` 用状态值 + `deleted_at/deleted_by_type/deleted_by/delete_reason` 四元组审计，T4）。核心关系走 41 条物理外键，而多态/审计/跳转类引用（`report.target_*`、`credit_log.ref_*`、`notification.ref_*`、`operation_log.target_*`、`deleted_by`）只做逻辑外键，靠 `OrphanScanTask`（每日 03:30）扫描失效引用，**只统计 + WARN 告警、绝不删除**（T3）。

6. **订单来源如何做到可追溯？**
   每个订单强制携带唯一来源且类型匹配：SALE→`goods_id`；PURCHASE→被接受的 `offer_id` + `want_post_id`；SWAP→被接受的 `swap_request_id` + `swap_post_id`（PRD §4.3）。三种来源统一复用 `OrderServiceImpl#createTransactionOrder` 建单，`loadSourceTitles` 回查来源帖子标题补齐 `order_info` 无标题快照列的展示需求。

7. **SWAP 订单为什么要双方分别确认？**
   交换是双向交付，任何一方单方"完成"都不代表交易成立。故 SWAP 记录 `buyer_confirmed_at` 与 `seller_confirmed_at`，**双方都确认才 `COMPLETED`**（T7）；重复确认不重复产生信用分（幂等事件键）。SALE/PURCHASE 则卖家单方确认收款即可完成。

8. **敏感词 DFA 怎么支持热更新？**
   `SensitiveWordServiceImpl` 用 DFA（确定有限自动机）构建词库并在发布、编辑、聊天、评价的文本入口统一校验，命中返回 40001 并附命中词列表。词库支持运行期刷新（增删改后重建自动机），种子 95 词写入 `schema.sql`，无需重启即可生效。

9. **JWT 双 token 的设计是什么？**
   登录签发 access token（2 小时，可访问业务接口）与 refresh token（7 天，仅用于 `/api/auth/refresh` 换发）。`AuthInterceptor` 校验 `TYPE_REFRESH` 的 token **不得访问业务接口**（返回 40101）；access 过期由前端 401 拦截 + refresh 静默换发。JWT 密钥不入库、不入 Git，dev 用演示默认值、prod 走环境变量。

10. **受限与封禁的拦截层次是怎样的？**
    分两层：**封禁**由 `AuthInterceptor` 每请求调用 `UserServiceImpl#applyFreshState` 在拦截器层统一拦截（`status=BANNED` 抛 `ACCOUNT_BANNED`，到期自动解封），对全部前台接口生效；**受限**在各业务 Service 入口校验（信用 <60 抛 `ACCOUNT_RESTRICTED`），覆盖下单、发布求购/交换帖、应约、发起交换、接受应约/同意交换。拦截器同时把 `authStatus/creditScore` 刷进 `LoginUser` 快照，业务层直读避免重复查库。

11. **派生计数（未读/收藏数/热度）如何保证可重建？**
    计数一律"事实表 + 唯一约束 + 事务内原子增减"，另设每日 03:30 定时重建兜底（`ChatServiceImpl#rebuildDerivedFields` 重建会话未读、`RecommendTask` 重算 `heat_score`），可从事实数据重建，不会因重复请求变成负数或重复累加（T5）。
